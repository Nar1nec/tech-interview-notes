
**Репликация** — механизм синхронизации нескольких копий базы данных. Каждая копия называется репликой.

### Зачем нужна репликация?

- **Доступность** — при падении одного сервера другие продолжают работу
- **Надежность** — защита от потери данных
- **Производительность** — увеличение скорости чтения
- **Геораспределение** — данные ближе к пользователям

### Типы репликации по времени

| Тип | Как работает | Плюсы | Минусы |
|-----|--------------|-------|--------|
| **Синхронная** | Клиент ждет подтверждения от всех реплик | Максимальная надежность, нет потери данных | Медленнее, зависимость от сети |
| **Асинхронная** | Клиент получает подтверждение сразу | Быстро, не зависит от сети | Возможна потеря данных при сбое |

### Виды репликации по реализации

**Физическая репликация**
- Копируется весь объем данных
- Полная точность
- Используется в PostgreSQL (WAL shipping)

**Логическая репликация**
- Копируются только изменения
- Экономия ресурсов
- Работает между разными версиями СУБД

### Топологии репликации

**Master-Slave (Active-Standby)**

```text
     [Клиенты]
         ↓
    [Мастер] ← пишем сюда
     ↙    ↘
[Реплика1] [Реплика2] ← читаем отсюда

- Один мастер принимает записи
- Несколько реплик для чтения
- При отказе мастера — переключение
```

**Master-Master (Active-Active)**

```text
[Клиенты1] → [Мастер1] ←→ [Мастер2] ← [Клиенты2]
                 ↖         ↗
               репликация в обе стороны
```

- Несколько мастеров принимают записи
- Данные реплицируются в обе стороны
- Требуется разрешение конфликтов
### Проблемы репликации
⚠️ **Конфликты при асинхронной репликации**
Два сервера одновременно меняют одну запись — нужен механизм разрешения конфликтов.
⚠️ **Несогласованность данных**
- Задержка репликации (replication lag)
- Чтение устаревших данных с реплик

### Replication Lag (задержка репликации) ⏱️

Это когда данные уже есть на Master, но еще не дошли до Slave.

**Пример:**
```sql
-- 10:00:00 на Master
INSERT INTO posts VALUES (100, 'Новый пост');
-- 10:00:01 кто-то читает с Slave
SELECT * FROM posts WHERE id = 100;  -- пусто! поста еще нет
-- Данные появятся на Slave в 10:00:02
```

**Как бороться:**

- Критичные данные читать с Master
- Остальное можно с Slave
- Мониторить задержку

### Что может сломаться? 💥

**Если упал Master (при Master-Slave)**
```text
Было: [Master] → [Slave1] [Slave2]
Стало: [упал Master] [Slave1] [Slave2]
Читать можно, писать нельзя!
Решение: сделать один из Slave новым Master
```

**Если упал Slave**

```
Было: [Master] → [Slave1] [Slave2] [Slave3]
Стало: [Master] → [Slave1] [Slave2] [упал Slave3]
Ничего страшного, остальные работают
Новый Slave3 можно поднять с копии данных
```
