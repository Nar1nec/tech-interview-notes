### Что такое шардирование?

**Шардирование** — это когда ты режешь одну большую базу данных на много маленьких кусочков (шардов) и раскладываешь по разным серверам.

> 📦 **Простая аналогия:** 
> 
> Представь, что у тебя огромный склад с товарами. Он забит под завязку, проходы узкие, искать что-то — целая проблема.
> 
> **Шардирование:** ты берешь и делишь товары на 10 маленьких складов. На первом складе — товары на букву А-В, на втором — Г-Е и так далее. Теперь искать быстрее, места хватает.
---
### Зачем это нужно? 🤔
Когда база данных становится слишком большой для одного сервера:
**Признаки, что пора шардировать:**
- 🔴 База весит терабайты и не влезает на диск
- 🔴 Один сервер не справляется с нагрузкой (CPU 100%)
- 🔴 10 000+ запросов в секунду
- 🔴 Резервное копирование длится часами
---
### Как это работает? ⚙️
#### До шардирования:

[Один огромный сервер]  
Вся база: 10 ТБ  
Все пользователи: 10 млн  
Все заказы: 100 млн

#### После шардирования:

```text
[Сервер 1] [Сервер 2] [Сервер 3]  
Пользователи 1-1000 Пользователи 1001-2000 Пользователи 2001-3000  
Заказы 1-10000 Заказы 10001-20000 Заказы 20001-30000
```

---
### Ключ шардирования (самое важное!) 🔑
**Ключ шардирования** — это правило, по которому ты решаешь, на какой сервер положить данные.
#### Пример с пользователями:
```sql
-- Ключ: user_id
-- Правило: user_id % 3 = номер сервера
user_id = 1 → 1 % 3 = 1 → сервер 1
user_id = 2 → 2 % 3 = 2 → сервер 2
user_id = 3 → 3 % 3 = 0 → сервер 3
user_id = 4 → 4 % 3 = 1 → сервер 1
```

### Виды шардирования

#### 1. Диапазонное:
```text
Шард 1: пользователи id 1 - 1 000 000
Шард 2: пользователи id 1 000 001 - 2 000 000
Шард 3: пользователи id 2 000 001 - 3 000 000
```
```sql
-- Знаем id = 1 500 000 → идем в шард 2
SELECT * FROM users WHERE id = 1500000;
```
✅ **Плюс:** Просто, легко добавлять диапазоны  
❌ **Минус:** Если все новые пользователи активны, последний шард перегружен
#### 2. Хешированное (Hash-based)

Считаем хеш от ключа и берём остаток:

```sql
-- Номер шарда = hash(user_id) % количество_шардов
shard_id = hash(12345) % 4 = 2 → данные в шарде 2
```

✅ **Плюс:** Равномерное распределение  
❌ **Минус:** При добавлении шарда все данные пересчитываются

#### 3. Круговое (Ring-based)

Шарды расположены по кругу, каждый отвечает за свой диапазон хешей:

```text
         [Шард 3]
          /  \
         /    \
 [Шард 2]      [Шард 4]
    |            |
    |    [Шард 1]|
    |    /    \  |
     \ /      \ /
     [Шард 0] [Шард 5]
```

✅ **Плюс:** Легко добавлять новые шарды  
❌ **Минус:** Сложнее реализовать

### Как понять, где данные? 🔍

Нужна **карта шардов** — табличка, которая знает, что где лежит.

```text
Карта шардов:
┌────────────┬─────────────┐
│ user_id    │ shard_id    │
├────────────┼─────────────┤
│ 1-1000     │ 1           │
│ 1001-2000  │ 2           │
│ 2001-3000  │ 3           │
└────────────┴─────────────┘
```



**Запрос:**

1. Смотрим в карту: user_id = 1500 → шард 2
    
2. Идем на сервер шарда 2
    
3. Выполняем запрос

### Проблемы шардирования 💥

#### 1. Запросы к нескольким шардам

```sql
-- Плохо: нужно обойти все шарды
SELECT AVG(balance) FROM users;  -- средний баланс всех пользователей
-- Надо опросить шард 1, шард 2, шард 3, сложить результаты
```

**Решение:** Хранить агрегаты отдельно или мириться с медленностью

#### 2. JOIN между шардами

```sql
-- Запрос к данным из разных шардов
SELECT * FROM orders o 
JOIN users u ON o.user_id = u.user_id  -- o в шарде 2, u в шарде 1
WHERE o.id = 100;
```

**Решение:** Денормализация (хранить дублирующие данные)

#### 3. Горячие шарды

```text
Шард 1: пользователи А-Г (мало запросов)
Шард 2: пользователи из Москвы (активные) → перегружен
```

**Решение:** Выбирать ключ, который равномерно распределяет нагрузку

#### 4. Перешардирование

Когда нужно добавить новый сервер и перераспределить данные:

```text
Было: 3 шарда
Стало: 4 шарда
Нужно: переложить часть данных с 1,2,3 на 4
```


**Решение:** Останавливать систему на время или делать онлайн-миграцию

### Когда нужно шардировать? 🎯

|Ситуация|Надо ли шардировать?|
|---|---|
|База 50 ГБ, нагрузка небольшая|❌ Не надо|
|База 500 ГБ, но чтений мало|❌ Вертикальное масштабирование|
|База 5 ТБ, 10 000 запросов/сек|✅ Пора|
|База 50 ТБ, нагрузка растет|✅ Срочно!|
